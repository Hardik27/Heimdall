Modular and Scalable Tech Stack for Tofia

Tofia’s tech stack is designed for modularity, scalability, and future extensibility (e.g. adding Retrieval-Augmented Generation or EMR APIs later) while following the general voice AI pipeline model ￼. Key components of the stack include:
	•	Telephony & Voice Interface: Vapi.ai for handling inbound and outbound voice calls. Vapi provides phone numbers (or integrates with Twilio) and manages call routing. It converts voice to text and vice versa using built-in Speech-to-Text (STT) and Text-to-Speech (TTS) services ￼. This allows Tofia to listen to callers and speak back in natural language. (Vapi even allows using custom AI “assistants” per number or dynamic assignment via webhooks ￼.) For SMS, Tofia will use a service like Twilio (Programmable SMS) to send appointment confirmations to patients.
	•	Conversational AI Engine (LLM): OpenAI GPT-4 (denoted GPT-4o) will serve as the brain of the assistant. GPT-4 handles intent understanding, context interpretation, and generation of natural-language responses. This large language model enables Tofia to carry on flexible dialogues, ask relevant follow-up questions, and adapt to various scenarios. Boardy’s rich, human-like conversations were likely enabled by such advanced AI integrations ￼. We will access GPT-4 via OpenAI’s API (or Azure OpenAI for HIPAA compliance) and design system prompts to guide its behavior (e.g. a patient-agent prompt and a hospital-agent prompt with appropriate tone and instructions).
	•	Memory and Data Persistence: A database (e.g. PostgreSQL for structured data, or MongoDB for flexible documents ￼) will store caller profiles and call records. Each caller (identified by phone number) will have a record of past interactions: summaries of previous calls, any provided personal details (name, insurance, etc.), and outcomes (e.g. appointment times). This persistent memory enables the AI to recognize repeat callers and recall context across calls – a feature Boardy used to build trust by remembering details over time ￼. Additionally, a vector store (like milvus) can store semantic embeddings of call transcripts or summaries. This allows Tofia to perform quick semantic look-ups – for example, if a patient asks “When is my next appointment?”, the assistant can retrieve that information from the vector index or DB rather than relying solely on GPT-4’s internal memory. All stored data will be encrypted and handled in a HIPAA-compliant manner (ensuring no sensitive info is logged or exposed).
	•	Backend Server & Orchestration: A Python backend (using a modern framework like FastAPI for async capabilities or Django for robustness) will orchestrate the interactions between components. This server hosts the logic for call handling and integrates with Vapi via webhooks/SDK. For instance, when an inbound call arrives, Vapi will invoke our backend (webhook) with the caller’s number and transcribed text; our server will then query the memory DB, call the GPT-4 API for a response, and return the reply to Vapi for TTS playback. The backend also contains the workflow logic that decides when to terminate the patient call and initiate the outbound call to the hospital. We’ll design this logic as a modular service (possibly as a separate “Call Orchestrator” module) so that it’s easy to modify (for example, integrating an API call to an EMR in the future instead of a phone call).
	•	Outbound Call & Integration Module: Tofia will use Vapi to place outbound calls to clinic/hospital reception desks. An AI agent will speak to the human receptionist to book appointments. This requires a slightly different dialog style, so we’ll configure a hospital-facing agent (using a distinct system prompt emphasizing professionalism, brevity, and clarity). Vapi allows specifying a temporary assistant profile when making an outbound call ￼; our backend will supply the patient’s info (from memory) and request the appointment through this profile. After the call, the system can capture the result (either via Vapi’s call transcript or a structured summary that the agent provides) and update the patient’s record. Finally, the integration module triggers the SMS to the patient with the confirmed details. (In the future, this module can be extended to integrate directly with hospital scheduling APIs or other services instead of a phone call.)
	•	AI Knowledge & Reasoning Modules (Future-Ready): While not in the initial scope, the architecture leaves room for plugging in additional AI modules, such as a RAG system for answering patient questions with verified medical or clinic policy info, or an analytics module to analyze calls. Because the core is modular, we could add a “Knowledge Base Q&A” microservice or an API integration (e.g. insurance verification service) without overhauling the entire system.

Each component is decoupled and communicates through well-defined interfaces (e.g., the Telephony interface delivers text to the Conversation engine; the Conversation engine calls the Memory module for context retrieval). This modular approach aligns with the traditional voice AI architecture of separate STT, NLP/LLM, and TTS stages ￼, which is easier to maintain and swap out components (for example, switching to a different LLM or voice service) than an end-to-end monolith. It’s also scalable: individual services (like the GPT-4 processing or the database) can be scaled horizontally as call volume grows, and stateless components can run in container orchestration (Kubernetes) for resilience.

System Components and Communication Flow

Below is a breakdown of how Tofia’s components work together during a typical use case – a patient calling to schedule an appointment, which triggers an outbound call to a hospital receptionist. This illustrates the responsibilities of each module and their interactions:
	1.	Inbound Call Initiation (Telephony Gateway): A patient dials Tofia’s phone number. The call is handled by Vapi.ai, which immediately handles low-level telephony (call routing, audio streaming). Vapi either has an AI assistant linked to this number or uses a webhook to fetch the appropriate assistant based on the caller’s number ￼. In our case, we use the webhook method to implement custom logic: Vapi sends our backend a notification of an incoming call with the caller’s phone number (Caller ID).
	2.	Caller Identification & Context Retrieval (Memory Module): Upon receiving the call event, our backend checks the Memory database for the caller’s number.
	•	If the caller is recognized (exists in DB), Tofia retrieves their profile and last call summary. For example, it might find that this caller is John Doe who called 2 months ago to schedule a check-up.
	•	If it’s a new caller, the memory module will create a new entry for this phone number and mark them as a first-time caller. No prior context is loaded, but this status will inform the conversation flow.
	3.	Automatic Speech Recognition (STT): As the patient speaks, Vapi’s STT engine transcribes the speech to text in real-time ￼. (Under the hood, Vapi uses advanced speech recognition – potentially deep learning models – to achieve high accuracy, even for medical terminology.) The transcribed text is passed to our Conversation engine.
	4.	Conversation Engine – Patient-facing Agent (LLM Logic): The GPT-4-powered agent processes the incoming text along with any relevant context. We construct a prompt for GPT-4 that includes:
	•	A system message defining Tofia’s role and behavior (e.g. “You are Tofia, a friendly healthcare assistant. You greet the patient, gather their request and necessary info politely, and speak in a calm, empathetic tone.”).
	•	If available, an appendix with context from memory (for instance: “(The caller’s name is John Doe, last call summary: scheduled check-up for 10/12/2024.)”).
	•	The transcribed user message (patient’s last utterance) as the user prompt.
GPT-4 analyzes the patient’s request and determines the intent. For example, the patient might say, “Hi, I need to book an appointment with Dr. Smith next week.” GPT-4 will recognize the intent to schedule an appointment and identify any missing pieces of information (e.g., patient’s full name if not already known, their insurance details if required by the clinic, the exact day/time preference, etc.). It then generates an appropriate response. This may be a follow-up question if more info is needed: e.g. “Sure, I can help with that. May I have your name and date of birth to locate your records?”. Because our system explicitly supports follow-up dialog, GPT-4 will continue a multi-turn conversation with the patient, guided by the system prompt to collect all necessary details.
	5.	Dialogue Management & Slot Filling: The patient-agent loop continues, potentially across several turns. Tofia (via GPT-4) uses dynamic prompts to handle this:
	•	For first-time callers, it will ask for onboarding information (like name, DOB, insurance provider) one by one, remembering answers provided. This is analogous to “slot-filling” in traditional IVR systems, but here driven by GPT-4’s understanding. (Our prompt and code logic ensure that once Tofia has, say, captured the insurance info, it won’t ask again in the same call.)
	•	For known callers, Tofia can skip directly to the issue at hand, using their name in conversation for a personalized touch (e.g., “Hi John, welcome back! Are you looking to follow up on your last appointment or schedule a new one?”).
	•	Tofia’s conversation engine keeps track of the dialogue state (which pieces of info have been obtained, what the user’s goal is). The modular design could include an explicit state machine or simply rely on GPT-4’s memory within the call. (We can reinforce the needed structure via the system prompt or few-shot examples, ensuring GPT-4 asks for any missing context.)
	6.	Decision Point – Handoff to Scheduling: Once the patient’s intent is clear and all necessary information is gathered, the conversation engine determines that it’s time to contact the hospital. For example, after confirming the patient needs an appointment with Dr. Smith on a preferred date, Tofia might say: “Thanks! Please hold while I arrange that with the clinic. I’ll be right back with confirmation.” The patient call is then gracefully ended or put on hold. In our architecture, we will likely end the call and call the patient back or send an SMS after, since doing a live hold and simultaneous call adds complexity. (Ending the call also saves the patient’s time – they don’t have to wait on the line during the backend process.)
	7.	Outbound Call to Hospital (Telephony & Orchestration): With the patient off the line, the Call Orchestrator module in the backend now initiates an outbound call via Vapi to the appropriate hospital or clinic number. It uses the Vapi SDK or API (/call endpoint) to dial out ￼. In the API request, our server attaches a specialized assistant profile or prompt for this call:
	•	The system prompt for the hospital-facing agent might be: “You are an AI assistant calling from [Clinic Name] on behalf of a patient to schedule an appointment. You speak formally and clearly, and will provide the patient’s details and request an appointment date. Be succinct and polite with the human receptionist. Do not reveal you are an AI unless asked.” We include the patient’s name, requested doctor, and any relevant info in this prompt so the AI can immediately present it.
	•	We select a voice for this agent that sounds professional (it could be the same voice or a different one from the patient-side agent, as long as it’s high-quality and understandable).
Vapi connects the call to the hospital. When the receptionist answers, the STT transcribes their greeting, and our hospital-agent GPT-4 (via Vapi or via our webhook) formulates a response to state the purpose: e.g. “Hello, I’m calling from Dr. Smith’s scheduling service on behalf of a patient, John Doe. John would like an appointment next week. Could you help find an available slot?”
	8.	Two-Way Dialog with Receptionist: A live dialog ensues between the AI agent and the human receptionist. This is a true test of the system’s conversational robustness, as the receptionist might ask questions or provide options. The STT/LLM/TTS loop handles each turn:
	•	Receptionist might ask for additional details (“What is the patient’s date of birth?”). The AI agent (GPT-4) has that info from earlier and responds from memory: “His date of birth is 08/12/1985.”
	•	The agent may need to negotiate an appointment time. The receptionist could say, “Dr. Smith is available on Monday at 9 AM or Wednesday at 4 PM.” The AI will choose one (perhaps based on patient’s stated preference, or if not given, just pick the earliest) and respond: “Wednesday at 4 PM works. Please book that. Thank you!”.
	•	If any unexpected questions arise (e.g. about something not in Tofia’s data), the agent is instructed to handle it gracefully or fallback. For instance, if asked for an insurance ID number that wasn’t collected, the AI could respond, “I’ll have the patient provide that to you shortly. For now, please pencil in the appointment.” (And we’d note to gather that from the patient via follow-up.)
Throughout this call, our backend may be recording or transcribing the conversation (Vapi can provide a transcript or our GPT agent can summarize as it goes). This ensures we capture the outcome.
	9.	Completion of Hospital Call: Once the appointment is successfully scheduled, the hospital-facing agent thanks the receptionist and ends the call. We now have the result (e.g. “Appointment confirmed for Wed, Mar 10 at 4:00 PM with Dr. Smith”). Vapi or our backend will capture this result data. For example, Vapi might trigger a webhook with the conversation transcript or final AI message. If not, we at least know the call succeeded and can parse the last AI response we generated for the confirmed time.
	10.	SMS Confirmation to Patient: Tofia’s integration module now sends an SMS to the patient’s phone number (using Twilio’s API or similar). The text message contains a concise confirmation, e.g.: “Your appointment with Dr. Smith is confirmed for Wed, Mar 10 at 4:00 PM. Location: ABC Clinic. Reply if you have questions.”. This SMS provides a written record for the patient. (Optionally, we could also trigger an outbound voice call to the patient with TTS reading the confirmation, but SMS is simpler and was requested.)
	11.	Memory Update and Persistence: After both calls, the system updates the Memory database. We save:
	•	A summary of the patient interaction (e.g. “03/01/2025: Patient John Doe requested appointment with Dr. Smith. Collected insurance info (Aetna) and DOB.”).
	•	A summary of the hospital call outcome (e.g. “03/01/2025: Booked appointment for 03/10/2025 4PM with Dr. Smith at ABC Clinic.”).
	•	Any new data obtained (if John was new, now we have his name, DOB, insurance on file).
	•	We also link the two call records with a common session ID or timestamp, so later we can retrieve the full context of the “appointment scheduling on 03/01/2025”.
	12.	Subsequent Calls & Persistent Context: In the future, when John calls again, Tofia will recognize his number and greet him by name, with awareness of his upcoming appointment or last interactions. For example: “Hello John, welcome back! Are you calling about your appointment on March 10th, or something else I can assist with?”. The persistent memory allows such personalized and contextually relevant dialogue, improving user experience and efficiency. Users can even ask questions about past calls (“What did you schedule for me last time?”), and Tofia can answer from the stored summaries.
	13.	Scalability & Monitoring: Each interaction flows through the modular pipeline described. For scaling, multiple instances of the conversation agent can run in parallel to handle concurrent calls. We will also include monitoring (logging call events, durations, any errors) and fail-safes. If the AI fails to understand or a service is down, we might fall back to a standard message or route the call to a human operator as a last resort. These operational considerations ensure the system can handle real-world conditions reliably.

This end-to-end flow shows how Vapi, the GPT-4 engine, the memory DB, and the orchestration logic all communicate:
	•	Vapi handles the audio interface, invoking our backend for AI decisions.
	•	The backend’s logic layer (orchestrator) connects the dots between STT/TTS services and the GPT-4 API, and between the patient side and hospital side.
	•	The memory service is queried at call start and updated at call end, providing continuity between sessions.
	•	External APIs (SMS gateway, future integrations) are called at the appropriate steps (post-call).

By adhering to this design, Tofia remains modular – for instance, if we later integrate an EMR API, we can insert a step in the flow after the hospital call (or replace the hospital call entirely with an API call to schedule). Or if we add a knowledge base, the GPT-4 agent can be augmented with retrieval from that source during conversation (the architecture can accommodate an extra knowledge query before GPT responds). Each component can be improved or swapped independently (e.g., using a more advanced ASR model or a different LLM) as long as it respects the input/output interface defined for that module.
